# Schema Optimizations — enterprise-project (`users`)

## What changed and why

### 1. Email uniqueness constraint `uq_users_email`

**Before**
```sql
email VARCHAR(255) NOT NULL   -- no unique constraint
```

**After**
```sql
email VARCHAR(254) NOT NULL,
CONSTRAINT uq_users_email UNIQUE (email)
```

**Rationale**  
Two users could register with the same email address. The application treats
email as a login/identity field; without a DB-level constraint a race condition
between two concurrent registrations could produce duplicate rows that no
application-side check catches. A unique constraint is the only reliable guard.

RFC 5321 §4.5.3 caps an email address at 254 characters. `VARCHAR(255)` accepts
one byte more than the spec allows and wastes a byte on every row.

---

### 2. Username unique constraint renamed to `uq_users_username`

**Before**
```sql
CONSTRAINT "UKr43af9ap4edm43mmtq01oddj6" UNIQUE (username)
-- name generated by Hibernate hash; differs per JVM run
```

**After**
```sql
CONSTRAINT uq_users_username UNIQUE (username)
```

**Rationale**  
Auto-generated constraint names are not deterministic across databases or
Hibernate versions. A migration script cannot reliably reference
`UKr43af9ap4edm43mmtq01oddj6` — it may not exist under that name in QA while
being present in prod. Named constraints make migrations idempotent and
referable in `ALTER TABLE` and diagnostic queries.

---

### 3. Column lengths

| Column   | Before | After | Reason |
|----------|--------|-------|--------|
| username | 255    | 50    | Industry convention; reduces row size; aligns with notification-service snapshot length |
| email    | 255    | 254   | RFC 5321 maximum |

**Storage impact (PostgreSQL)**  
`VARCHAR(n)` in PostgreSQL stores only the actual length; `n` is purely a
constraint, not a reserved allocation. The length reduction itself saves no
on-disk space for existing rows. The benefit is that the DB rejects
oversized values at insertion time rather than silently truncating or
throwing a generic error.

---

### 4. Stable pagination sort `ORDER BY id`

**Before**
```java
@PageableDefault(size = 50)  // no sort specified
```

**After**
```java
@PageableDefault(size = 50, sort = "id")
```

**Rationale**  
Without an explicit `ORDER BY`, a paginated query returns rows in heap order,
which is non-deterministic and changes as rows are inserted, updated, or
vacuumed. A caller requesting page 2 can receive rows it already saw on page 1,
and other rows may never appear.

`id` (the sequence-assigned primary key) is the cheapest stable sort: it is
already indexed, and its ascending order approximates insertion order.

---

## Query plan impact

### `GET /api/v1/users` (getAllUsers)

Before (no ORDER BY):
```
Seq Scan on users  (rows=N)
  -- non-deterministic, repeatable page overlap possible
```

After (`ORDER BY id`):
```
Index Scan using users_pkey on users  (rows=N)
  -- PK index used; no sort step
```
